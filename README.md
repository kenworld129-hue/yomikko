## 概要

「よみっこ」は、ひらがなに興味を持ち始めた3歳児が、自分でタップして遊びながらひらがなの **「読み」** を練習できる iOS アプリです。

### コンセプト

- **「読み」に特化**。書きはアナログ（紙とペン）で学ぶべきという理念のもと、書き機能は持ちません。
- **写真カスタム登録による差別化**。親が子供の好きな写真や単語を登録できます。「家族の犬」「お気に入りのおもちゃ」など、その子だけの教材を作れます。
- **写真は後から外せる**。登録した写真・イラストは取り消して「文字だけで読む」状態に戻せます。絵は読みの“補助輪”という位置づけで、子の育ちに合わせて親が外せる設計です。
- **写真は端末ローカル保存のみ**。サーバー送信なし、外部送信される個人情報を扱わないシンプルな設計。

## 主な機能 (v1)

- プリセット20語 + 親登録のカスタム単語による読み練習
- 自動音声モード（出題ごとに「くるま、どれかな？」と自動読み上げ、`AVSpeechSynthesizer` 速度0.4固定）
- 読み上げ中はマスコットが口パクで案内（音声の開始・終了に同期した2コマアニメーション）
- 正解タップで効果音と大きな○マーク・カード拡大の演出、約2秒後に次の問題へ自動遷移
- 不正解タップは押したカードに ✗・正解カードに枠線・不正解音で軽くフィードバックし、次の問題へ（1問1タップ勝負）
- ゲーム途中の中断（「やめる」→確認シートで誤タップを防いでホームへ）
- 写真アップロード（フォトライブラリから選択）
- 10問1セッション。結果画面は正解数ぶんの○と「10もんちゅう8もんせいかい！」の表示＋自動読み上げ、正解数に応じた4段階のお祝い（8問以上で紙吹雪・マスコットがはねる）
- 写真未設定の単語には汎用イラストを自動割り当て
- プリセット20語を初期状態へ復元（削除・改名・写真変更したプリセットを購入時のイラストに戻す）

## 技術スタック

| 項目 | 採用技術 |
|------|---------|
| アーキテクチャ | SwiftUI + `@Observable` |
| データ永続化 | SwiftData |
| 音声合成 | AVSpeechSynthesizer |
| 写真連携 | PhotosUI |
| テスト | Swift Testing |
| ターゲット OS | iOS 17+ |
| 開発環境 | Xcode 26.6 |

### 設計判断の根拠

- **SwiftData を採用**（CoreData ではなく）：iOS 17 から登場したモダン API。`@Model` マクロで宣言的にスキーマを定義でき、SwiftUI との統合が一級。学習コストはあるが、最新 API での実装経験を積むことを優先。
- **書き機能を持たない**：機能スコープを絞ることでリリース距離を短縮。同時に「書きはアナログで」という育児上の理念を表明する役割も持たせている。
- **写真はローカル保存のみ**：プライバシー配慮とサーバー実装コスト回避を兼ねる。これにより GDPR 等のデータ越境問題からも切り離せる。
- **カメラ撮影は非対応**（フォトライブラリ選択のみ）：「いまの瞬間を撮る」のはカメラアプリの役割であり、本アプリの責務（ひらがな読み練習）の外と整理した。`PhotosPicker` 一択にすることで、権限ダイアログや `UIImagePickerController` のラップも不要になり実装がシンプルになる。
- **`@Observable` を採用**（`ObservableObject` ではなく）：iOS 17 のマクロベースの新方式。再描画粒度が細かくパフォーマンス的にも有利。
- **読み上げ音声はフォールバック付きの優先選択**：既定音声は機械的な compact 品質になりがちなため、端末内蔵のより自然な日本語音声を優先順（O-ren → Grandma → 既定）で選び、未搭載の端末では既定へ安全に落とす。アプリからシステム音声はダウンロードできない制約下で「その端末にある中での最良」を使う設計。
- **読み上げにマスコットの口パクを同期**：合成音声は幼児に機械的で怖く響きうるため、読み上げ中だけマスコットが口パクする演出で声を「このキャラの声」として意味づける（子供向けメディアの定番手法）。実装は `AVSpeechSynthesizerDelegate` の開始・終了通知を `@Observable` な状態にミラーし、`TimelineView` が現在時刻から口の開閉を導出する方式。タイマー等の命令的な資源管理を持たず、View の破棄と同時に後始末が完了する。
- **画面遷移は自前ルーティングで実装**（`NavigationStack` / `fullScreenCover` ではなく）：`@Observable` な `AppRouter` をアプリ全体で1つ Environment 注入し、ルート View が `switch` で表示画面を選択する方式。3歳児向け＋有料アプリとして UI を独自に作り込む方針上、画面切替トランジション演出まで自前で設計できる余地を確保する必要があったため、標準ナビゲーション API を意図的に外した。起動時免責モーダルのような「装飾不要・機械的トーンが意図と合致する」表示には標準 `.fullScreenCover` を併用し、責務に応じて標準 / 自前を使い分けている。
- **正解演出の進行は固定時間ウィンドウで制御**（効果音やアニメーションの完了イベント駆動ではなく）：正解タップで効果音・演出を同時に開始し、一定時間後に必ず次の問題へ進む。ゲーム進行という最も止めてはいけない動作を、再生失敗がありうる音声部品に係留しないための判断。同じ思想で、効果音ファイルの読み込み失敗時もクラッシュさせず無音で進行を継続する（効果音は無くてもゲームが成立する装飾、という責務整理）。
- **不正解は同じ問題を再出題せず、次の問題へ進む（1問1タップ制）**：当初仕様は「不正解なら同じ問題を再出題」だったが、実際の3歳児によるテストプレイで、再出題ルールでは不正解にコストがなく「カードを順に全部押せば必ず正解演出に届く」ため、読まずに連打する行動を観察。報酬（正解演出）が「考えて当てる」行動だけに与えられるよう進行ルールを改訂した。間違えた語の学習機会は、毎回ランダム抽出で同じ語が後のセッションに再登場する反復構造側で担保する。対象年齢の実ユーザーテストを起点に仕様を変更した記録として残す。
- **ゲーム中断は「確認シート＋退場処理の一点集約」**：3歳児は画面を連打する前提（上記の実プレイ観察）に立ち、「やめる」ボタン単発の誤タップで進行中セッションが消えないよう確認シートを挟む。中断確定時は、演出の自動進行を担う遅延タスクのキャンセル→読み上げ停止→画面切替を単一メソッドに集約。SwiftUI のフェード遷移中は退場した画面がまだ生きて動き続けるため、オブジェクト破棄任せにせず明示的に止める。Swift の Task キャンセルは協調的（キャンセルは要求フラグに過ぎず、検査コードを書いて初めて停止する）ため、スリープ後にキャンセル検査を挟み「中断確定後は音も進行も一切走らない」を保証した。
- **結果画面のお祝いは一律にせず、正解数に応じた4段階**：全問不正解でも盛大に祝う一律演出だと、「読んで当てたときだけ報酬がある」という1問1タップ制（上記）の報酬設計が最後の画面で崩れるため、score から4段階（満点／8問以上／1〜7問／0問）を導出して演出の強さを変える。3枚からの当てずっぽうでは8問以上に届く確率が約0.3%しかなく、最派手の演出（紙吹雪）は実質「読めた子だけが届く領域」になる。0問は祝う文言をやめて次への誘いに差し替え、事実と演出を一致させた。あわせて正解数そのものは、数字が読めない子にも伝わるよう「正解数ぶんの○を1個ずつ表示する」形で可視化した（ゲーム中に正解のたび出る○マークの集計として、記号の意味を一貫させている）。
- **アプリ内レビュー促進（SKStoreReviewController）は搭載しない**：当初は3セッション完了後に1回だけ表示する計画だったが、本アプリの使用モデルは「親が隣にいなくても子供が遊べる」であり、プロンプトが表示される瞬間に画面の前にいるのは文字が読めない3歳児になる。システムのレビューカードは星のタップで評価が実送信されるため、無視されて機会が消えるか、意図しない評価が送信されるかの二択となり、目的（レビュー獲得）に対して逆効果と判断して廃止した。プレイのリズムを割り込みで崩さないことを優先し、レビューは依頼ベースで集める方針。

### ビルド方法

```bash
git clone https://github.com/kenworld129-hue/yomikko.git
cd yomikko
open yomikko.xcodeproj

```
yomikko/
├── yomikko/                    # アプリソースコード
│   ├── App/                    # アプリエントリ・ルート View
│   │   ├── yomikkoApp.swift    # @main エントリポイント（ModelContainer 初期化・AppRouter 注入）
│   │   └── RootView.swift      # ルート View（画面切替の司令塔、switch + .fullScreenCover）
│   ├── Routing/                # 画面切替の状態管理

## 開発の背景

長年 COBOL 基幹システムの開発・運用に携わってきたエンジニアによる、SwiftUI / SwiftData を使ったモダン iOS 開発への挑戦記録です。「動くアプリ」だけでなく **「設計の意図が読めるリポジトリ」** を目指して、以下を意識して開発を進めています：

- 設計仕様を先に整備し、実装はそれに従う（仕様駆動開発）
- 各 Phase でのコミット粒度を、外部から進捗が読める単位に保つ
- 技術選定の理由をコード／README に明記する
